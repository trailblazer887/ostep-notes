\section{Visualization(CPU)}

\subsection{Mechanism: Limited Direct Execution}
即``有限制地"将进程放在CPU上直接执行.为了使这个机制正常工作,我们需要解决两个问题
\begin{enumerate}
    \item Restricted Operations \\
    为了保障系统安全,不能允许进程直接进行操作(读写I/O或申请CPU资源等``敏感操作"),因此我们用``分权"将进程和``敏感操作"隔离开,统一交给神圣的``操作系统"来管辖:设置\textbf{user mode}和\textbf{kernel mode},将进程能干的事限制在安全范围之内.你说你想读写I/O?问问操作系统吧! \\
    接着,OS,hardware,process,合作进行``敏感操作""(详细过程见本章中的流程图)
    
    \item Switching Between Processes \\
    进程切换方式分为\textbf{Cooperative Approach}和\textbf{Non-Cooperative Approach}.简单来说,前者靠进程自觉让出CPU控制权,假设每个进程都守规矩;而后者为了防止有心者恶意占用CPU资源,便设置\textbf{timer interupt}强制进程让出CPU以便给其他进程机会运行. \\
    进程切换也包括\textbf{上下文切换}(\textbf{context switch}).容易让人困惑的是,当实现进程A切换至进程B时,首先先将进程A的相关信息(registers,PC等)保存至hardware的每个进程相关kernel stack中,然后OS再将kernel stack中的信息转移至PCB中的相关部分,返回时过程类似,需重点理解.
\end{enumerate}

\subsection{Scheduling: Introduction}
\begin{enumerate}
    \item Scheduling Metrics \\ 
    Scheduling metrics有两大死对头：turnaround time和response time。要想平衡两者很困难（trade-off的艺术），由此也派生出两类调度方法（这里暂且认为每个进程的用时一致，即“上帝视角”）。
    \item Good for Turnaround Time \\
    其代表为\textbf{FIFO}(first in, first out)和\textbf{SJF}(short job first)(具有抢占式特点的则叫\textbf{STCF}(short time-to-completion first)或\textbf{PSJF}(preemptive shortest job first))。
    \item Good for Response Time \\
    其代表为\textbf{RR(Round Robin) scheduling}或\textbf{time-slicing}
    \item Incorporating I/O
    如果考虑I/O操作的话，我们可以使用\textbf{Overlap}思想，在一个进程执行I/O操作时，CPU去执行另外一个进程，提高CPU的利用率，同时减少时间浪费。
    \item No More Oracle \\
    但是我们并不是“上帝”，并不能提前知道一个进程总共要花费多长时间，SJF等方法就失效了。如何克服这个问题呢？在下一节我们会建立一个新的scheduler——\textbf{它能根据过去来预测未来}，也被称为\textbf{multi-level feedback queue}。
\end{enumerate}

\subsection{Scheduling: The Multi-Level Feedback Queue(MLFQ)}
\begin{enumerate}
    \item Basic Concept \\
    我们将进程分为两类:
    \begin{itemize}
        \item \textbf{Short-running}利用CPU较少，主要时间花费在I/O操作上（主要是交互型任务）。
        \item \textbf{Long-running}大量利用CPU，很少有I/O操作（例如批处理任务等）。
    \end{itemize}
    \textbf{MLFQ}构建多个具有不同优先级的队列，并在基础上进行调度，文中模拟了一个\textbf{简单的scheduler}，并不断优化以缓解\textbf{Stavation},\textbf{Security},\\
    \textbf{Behavior Changes}问题，其遵循以下规则：
    \begin{enumerate}
        \item 处于高优先级的进程优先执行，具有相同优先级的进程进行\textbf{RR scheduling}。
        \item 当一个进程进入调度范围，首先会被放在最高优先级队列中。
        \item 当某个进程在某个队列中被调度了一定的的CPU处理时间(看\textbf{时间的积累量}，不管是否中间有过I/O操作)，如果其值超过一定的阈值(\textbf{allotment})，就下调其优先级。
        \item 当经过一段时间$S$时，将全部进程的优先级提至最高。
    \end{enumerate}
    \item Reality
    实际上基于MLFQ的scheduler及其变体百花齐放啊，很多OS都在用，也有很多其他的调度策略（如\textbf{decay-usage}等）。同时管理者的提示（\textbf{advice}）也时很有用的，可以用\texttt{nice}来手动调整优先级，
    毕竟哪个进程优先，管理者心里有杆秤，也免了OS猜了。
\end{enumerate}
\subsection{Scheduling: Proportional Share}
\begin{enumerate}
    \item Basic Concept \\
    本章介绍了三种scheduling method: 
    \begin{itemize}
    \item \textbf{lottery scheduling}，具有随机性
    \item \textbf{stride scheduling}，具有决定性，stride和lottery成反比
    \item \textbf{complete fair scheduler}，以\textbf{virtual runtime}\texttt{(vruntime)}为标准，
    设置优先级，转换为权重计算\texttt{vruntime}，动态时间片
    \begin{equation*}
        \texttt{time\_slice}_{k} = \frac{\texttt{weight}_{k}}{\sum_{i=0}^{n-1} \texttt{weight}_{i}} \cdot \texttt{sched\_latency}
    \end{equation*}
    \begin{equation*}
        \texttt{vruntime}_{i} = \texttt{vruntime}_{i} + \frac{\texttt{weight}_{0}}{\texttt{weight}_{i}} \cdot \texttt{runtime}_{i}
    \end{equation*}
    \textbf{如何快速查找/添加减少“运行进程队列”里的成员呢？} \\
    用\textbf{红黑树}数据结构，善用数据结构减少payload也是scheduling method重要的一环！
    \end{itemize}
\end{enumerate}

\subsection{Paging: Introduction}

\subsection{Paging: Faster Translations (TLBs)}
由OS处理TLB不命中(将内存中的相应内容放到TLB里，再访问TLB)，同时为了防止\textbf{访存不命中死循环}(跳转到处理访存不命中的地址也需要翻译，而它也不在缓存中时，就会发生死循环)，可以\textbf{直接用物理地址}或\textbf{在TLB中设立常驻有效翻译}(valid = 1，其中\textbf{wired register}告诉硬件为OS保留多少个槽位)。\\
\indent 如果涉及到多个进程，则可以通过\textbf{重置valid = 0}或\textbf{设置address space identifier(ASID)位来区分不同进程的地址空间} \\
\indent \textbf{替换策略}: \textbf{LRU}

\subsection{Complete Virtual Memory Systems}
在前面介绍了许多虚拟内存的机制后，这一章我们通过两个系统的例子(\textbf{VAX/VMX}和\textbf{Linux})来看看完整的虚拟内存系统是怎么样搭建起来的。
\subsubsection{VAX/VMS}
\begin{itemize}
    \item Memory Management \\
    受限于硬件(VAX，页小，页表很大)，为了减少内存压力，VMS采用\textbf{分页与分段结合的混合策略}和\textbf{将进程页表放在内核虚拟内存中，可将页表换至磁盘中}
    \item A Real Address Space \\
    地址空间被分为User(P0, p1两段)和System(S)共三段，其中Page 0被标记为不可访问，用于检测\textbf{空指针访问}。
    \item Page Replacement \\
    为了防止一个用户进程占用太多内存(memory hogs)，故给每个进程设置能使用的页数最大值(\textbf{resident set size (RSS)})，而且每个页维护在一个FIFO表中，一旦页数超过最大值，
    就从该进程的FIFO表中移除一页，放在\textbf{second-chance lists}(分为\textbf{clear-page free list}和\textbf{dirty-page list})中，如果有进程需要，则可从clear-page free list中
    取页，同时，使用\textbf{clustering}的思想将dirty-page list的页聚集在一起写回磁盘，提高访问磁盘效率。
    \item Other Neat Tricks \\
    \textbf{demand zeroing}：当OS要分配一页给进程时(比如在heap中)，OS不会立马为它找一份空闲页，而是仅添加一个标记为不可访问的PTE。只有这一页被读或写时，会触发trap，OS(通常通过PTE中的代表\textbf{reserved for OS}的多个位)知道它时demand-zero page，这时才寻找空闲页，初始化，添加映射关系。 \\
    \textbf{copy-on-write}：在两个地址空间都映射到同一个物理页时，将该页设置为\textbf{只读}，如果都是进行读操作，则不会进行复制。唯有其中一个进行写操作时，触发trap，OS知道该页时COW页，这时才会分配新的页，复制数据，添加映射关系。

\end{itemize}
\subsubsection{Linux}
\begin{itemize}
    \item Address Space \\
    分为User和Kernel(分为Kernel(Logical)和Kernel(Virtual))，其中kernel(logical)为线性映射(即其对应的物理地址空间也是连续的)，且不能被swap到磁盘中，kernel(virtual)为非线性映射，使内核能映射大内存(在32-bit Linux中约为1GB)。
    \item Page Table Structure \\
    对于Linux for x86，其采用多级页表(通常为4级)。
    \item Large Page Support
    支持大于4KB的页，可以使得TLB的miss减少，但是可能导致\textbf{internal fragmentation}
    \item The Page Cache \\
    在内存中的page有三个来源：\textbf{memory-mapped files},\textbf{file data and metodata from devices},\textbf{anonymous memory}。page cache会追踪其中的页是clean还是dirty，dirty页会被后台线程周期性写回。\\
    Linux采用\textbf{2Q}替换算法，其存在两个list，一个是inactive list(A1，第一次访问时放入)，一个是active list(Aq，再次访问时放入)，要替换时就从A1中找一页提出。且Linux会周期性地将active list底部的页移动到inactive list中。2Q采用an approximation of LRU(与clock replacement相似)管理两个表。
    \item Security And Buffer Overflows \\
    应对\textbf{buffer overflow}的方法：使用\textbf{NX bit}(AMD)或\textbf{XD bit}(x86)。\\
    应对\textbf{return-oriented programming}(\textbf{ROP})的方法：\textbf{ASLR} \\
    应对\textbf{Meltdown and spectre}的方法：\textbf{kernel page-table isolation(KPTI)}
\end{itemize}

\subsection{Condition Variables}
有时，抢到锁之后也不会执行相关操作（因为\textbf{业务条件没满足}），这时就要通过\textbf{Condition Variables}来表征业务条件是否满足。本章主要介绍CV相关的问题。
\begin{itemize}
    \item The Producer/Consumer (Bounded Buffer) Problem\\
    根据情况，可能需要使用\textbf{多个CV} \\
    而且由于几乎所有的系统都信号的\textbf{Mesa semantics}（与之相对的是\textbf{Hoarse semantics}），即signal只是叫醒别人，不保证接下来一定会把CPU控制权交给它，
    即被叫醒并\textbf{不等于}之后抢到锁时CV为该线程所预期的状态，又由于\textbf{spurious wakeups}存在(一次signal可能会唤醒两个线程，即\textbf{线程会无缘无故的醒来})，两方面的原因导致使用\textbf{while}而不是if会更\textbf{可靠}。
    \item Memory allocation \\
    对于上述问题，CV只需两个即可。但是对于memory allocation，需要几个CV是未知的。唤醒free(50)和唤醒free(100)乃至各种各样free(...)的线程，在当前特定的语境下，效果都是截然不同的，无法通过可知数量的CV
    区分开。这时比较直接的方法为换\textbf{signal}为\textbf{broadcoat}，这种情况被称为\textbf{covering condition}，即把所有睡眠线程都唤醒。可能会导致性能下降。
\end{itemize}

\subsection{Common Concurrency Problems}
本章主要介绍了几种并发问题的类型及其解决方案 \\
并发bugs分为以下几种类型（及Deadlock prevention）： \\
\begin{itemize}
    \item Non-Deadlock Bugs \\
    分为\textbf{Atomicity-Violation Bugs}和\textbf{Ordering-Violation Bugs}
    \item DeadLock Bugs \\
    造成DeadLock的原因包括\textbf{复杂的相互依赖}和\textbf{封装的本性} \\
    死锁的发生有\textbf{四个必要条件}
    \begin{itemize}
        \item \textbf{Mutual exlusion} \\
        请\textbf{硬件}帮忙（例如\texttt{compare\_and\_swap}原语）
        \item \textbf{Hold-and-wait} \\
        一次性持有所有的锁（problematic solution）
        \item \textbf{No preemption}
        使用\texttt{trylock}，拿到L1锁没拿到L2，直接释放L1锁重新循环（可能造成\textbf{livelock}）
        \item \textbf{Circular wait} \\
        使用\textbf{total ordering}或\textbf{partial ordering}
    \end{itemize}
\end{itemize}
除了\textbf{静态}的deadlock prevention，还可以通过\textbf{动态}的deadlock avoidance，即通过\textbf{动态调整调度策略}来避免思索。另外，
如果死锁造成的风险不大，可以用\textbf{Detect and Recover}思想，周期性检测死锁，一旦检测到死锁发生，则重启整个系统（没有办法的办法，只有
死锁的代价不大时才可以这么做应付一下！！）
\subsection{Event-based Concurrency (Advanced)}
本章主要介绍的是\textbf{基于事件}的并发方法，由于只有一个主线程，所以没有线程在并发中的种种问题（死锁等） \\
以下为该方法的核心思想\textbf{Even Loop}:
\begin{Verbatim}[numbers=left, frame=single, formatcom=\color{black}]
while (1) {
    events = getEvents(); 
    for (e in events)  
        processEvent(e);
}
\end{Verbatim}
重要API：\texttt{Select()(or poll())} \\
该方法面临以下几个问题（以服务器为例）：
\begin{itemize}
    \item Blocking System Call \\
    当even handler中有\textbf{阻塞}的系统调用时，其他client即使准备好了，主线程因为阻塞而无法相应。可以通过\textbf{Asynchronous I/O + UNIX signals}解决（当然要尽量避免阻塞调用）。
    \item State Management \\
    如果使用AIO，那么当I/O调用完成时，如果像把信息传给之前调用的client，怎么知道要传给那个client呢（在基于线程的服务器中就无需担心，因为线程会将client信息存入自己的栈中）？
    我们可以手动维护一个数据结构，用来存放client相关信息（manual stack management）
\end{itemize}
当然，基于事件的并发还是有许多其他问题（比如多CPU的情况，对于隐式阻塞的无奈（如Paging，缺页后OS层面强制阻塞），对于API阻塞性的依赖（总是要注意更新时API阻塞性是否改变））等等。

\subsection{I/O Devices}
本章将对I/O设备的作基本介绍 \\
\indent 简单来说(并不实际)，I/O devices包括\textbf{interface}(status, command, data register)和\textbf{internals}(一些硬件，如micro-controller(CPU)等)两个部分。\\
\indent \textbf{device driver}就像OS的"翻译官"，将具体不同的硬件操作抽象化提供给OS，使得OS能够调用统一的接口来操作I/O。
\subsubsection{The Canonical Protocol}
\begin{itemize}
    \item 循环检查device状态，如果已准备好，便可执行下一步
    \item 将相关信息写入device register中(包括data和command) \\
    如果这一步主要由主CPU参与，则称之为\textbf{programmed I/O(PIO)}，如果不用主CPU参与则为\textbf{DMA}。\\
    可以用\textbf{特殊命令（explicit I/O instructions）}（如x86中的in,out）或\textbf{memory mapped I/O}（像访问内存一样访问devices）来访问device register，两种方法在现代OS中仍在使用。同时可以通过\textbf{driver}来抽象化。
    \item 等待直到device返回信息 \\
    可以分为\textbf{轮询等待}和\textbf{硬件中断}两种方法，可用两种方法的混合(\textbf{hybrid})。对于硬件中断的优化，可以采取\textbf{coalescing}，即在要发送中断信号时等待一段时间，可以将多个中断集中成一个中断一起处理，减少trap上下文的频繁切换。
\end{itemize}
\subsection{Hard Disk Drives}
本章主要介绍了HDD的组成部分以及相关调度策略。
\textbf{Interface}: sector（扇区），track（磁道），spindle（旋转轴），flatter（盘面），surface（盘面的上下面），disk head，disk arm。\\
通常硬件厂商只保证对\textbf{一个扇区}的读写是\textbf{原子}的。\\
HDD读写数据分为三个阶段：\textbf{seek} - \textbf{rotation} - \textbf{transfer}。 \\
为了减少一些额外的开销，HDD还采用\textbf{track skew}，\textbf{multi-zoned}，\textbf{cache/track buffer}等技术或思想。\\
根据“何时算写动作完成”分为\textbf{write back}（写到cache中）和\textbf{write through}（写到HDD中）\\
结论：平均寻道距离(seek distance)是完全寻道距离（从$0$到$N$）的\textbf{三分之一}（书中有详细推导）
以下介绍硬盘调度策略：
\begin{itemize}
    \item SSTF: Shortest Seek Time First \\
    但是有\textbf{starvation}的风险
    \item Elevator (a.k.a. SCAN or C-SCAN) \\
    可以解决starvation，但是没有遵循\textbf{SJF(Shortest Jobs First)}的原则，故性能不佳
    \item SPTF: Shortest Positioning Time First \\
    同时考虑$T_{seek}$和$T_{rotation}$，但是只靠OS难以实现，因为OS掌握的HDD底层信息（如当前盘面旋转的角度等）不足以其精准推测。故HDD里集成了\textbf{内部调度器}，
    根据当前HDD的状态信息进行调度。
    \item I/O merging \\
    适当调整I/O requests的顺序，将“欲访问的扇区相邻”的请求综合为一个总请求。所以，可以采用\textbf{anticipatory disk scheduling}（系统在发送I/O请求之前等待一会儿）来更好地实现聚合。
    与之相对的是\textbf{work-conserving}（有请求就直接发送）
\end{itemize}
\subsection{Redundant Arrays of Inexpensive Disks  (RAIDs)}
如何使disk\textbf{更快，更大，更可靠}呢？本章主要介绍\textbf{RAIDs}技术，及其分类和每种类型的性能分析。\\
\indent RAIDs是一个复杂的集合体，包括\textbf{multiple disks}, \textbf{memory(both volatile and non-)}, one and more \textbf{processors}，很像一个计算机系统。 \\
\subsubsection{Interface And RAID Internals}
文件系统发送一个\textbf{logical I/O request}给RAID，RAID通过计算将其转化为一个或多个\textbf{physical I/Os}。
\subsubsection{Fault Model}
本章主要关注\textbf{fail-stop}模型，在这个模型中，磁盘分为working和failed两种状态，且failed能被RAID控制器硬件捕捉到。还有更复杂的\textbf{silent failure(disk corruption)}, \textbf{latent sector error}，我们会在之后的章节进行讨论。
\subsubsection{Metrics}
有三个评价标准：\textbf{performance}, \textbf{throughout}, \textbf{latency}
\subsubsection{Categories}
\begin{itemize}
    \item RAID Level 0: Striping \\
    性能好，但是不可靠。
    \item RAID Level 1: Mirroring \\
    随机I/O性能好，可靠，但是容量少。
    可分为 常见的\textbf{RAID-10} (or RAID 1+0, stripe of mirrors)和较不常见的\textbf{RAID-01} (or RAID 0+1, mirror of stripes)。
    \item RAID Level 4: Saving Space With Parity \\
    容易遇到\textbf{small-write problem}，基本被level 5替代。
    \item RAID Level 5: Rotating Parity \\
    为了缓解small-write problem而在level 4上做出的改进。现实中基本上可以替代level 4。可靠和容量大，但是性能受small-write problem的影响。
\end{itemize}
\subsection{Interlude: Files and Directories}
本章主要介绍文件系统的相关概念以及一系列相关的API或系统调用。\\
目录：保存\textbf{文件名}和\textbf{inode}的映射关系 \\
文件：一串字节序列。\\
每个进程中，一个\textbf{fd(file descriptor)}指向一个\textbf{open file table entry}（所有进程共享），每一个表项由指向一个\textbf{inode table entry}，即索引到相应的inode结构体，根据inode结构体上指向数据块的指针即可索引到其对应的文件数据。\\
\textbf{mmap()} 通过将磁盘中的内容直接映射到内存中，可以进行对硬盘内容的直接访问，以此可以构建\textbf{持久化栈}等。 \\
\textbf{ACL(access control list)}：相对于\textbf{permission bits}提供了更为精确的权限控制。 \\
\textbf{TOCTTOU(Time of Check To Time Of Use) problem}：权限检查和执行操作的非原子化导致了潜在的提权漏洞。 \\
\textbf{mount}：将一个设备文件（例如\texttt{/dev/sda1}）应用于某种文件系统（如\texttt{ext4}）并挂载到相应目录下（例如\texttt{/home/users}），通过访问目录即可以该文件系统的形式访问设备（将设备中杂乱无章的字节流组织起来，并可通过相应目录访问）。
\subsection{File System Implementation}
本章主要介绍文件系统的一种简单实现(\textbf{vsfs, Very Simple File System}) \\
在\textbf{vsfs}中，首先将硬盘\textbf{分块}。硬盘上的数据结构如下：
\begin{itemize}
    \item super block \\
    包含\textbf{多少个inodes和data blocks、inode table的起始点、指示当前volume的文件系统类型的magic number}等等。
    \item inode/data bitmap \\
    指示特定位置的inode(以inode为单位)/data(以block为单位)是否被占用。当然也可以使用\textbf{free list}来实现此功能。
    对于\textbf{空闲空间管理}，可以采用\textbf{pre-allocation policy}，即一次性预分配一系列块给文件(而不是一块一块分配)，使得文件在磁盘上连续分布，提高性能。
    \item inodes table \\
    管理所有的inode(内含\textbf{文件长度、权限、文件数据块的位置(指针数组)}等)。
    \item data region \\
    存放文件中的数据(字节流)。
\end{itemize}
为了支持更大的文件，可以使用\textbf{The Multi-Level Index}，即使用\textbf{indirect pointer}来指向更多的"指向数据块的指针"。
也可以使用\textbf{entents-based approach}，即不是"一个指针指向一个块"，而是"一个指针和一个长度指示一系列块"，但是这种方法要求块分配的连续性。
还可以使用\textbf{linked-based approach}，即inode保存指向起始块的指针，而且在当前块的末尾保存指向下一个快的指针(像"链表"一样将数据块串在一起)。
但是这样会使随机访问会有很大的性能开销，于是可以采用\textbf{将链接信息存放在内存中}的优化方法，在内存中保存一个\textbf{FAT(file allocation table)}，其中$FAT[\text{当前块号}]=\text{指向下一个块的指针}$ \\
书中详细讲述了读写磁盘的全流程(详细过程见书)。执行一次简单的文件读写就要进行多次I/O操作，于是可以在内存中分出一部分用来作为\textbf{热门块的cache}，由此分出\textbf{static partitioning}(在启动时便分配若干个固定大小的内存用来作为cache)和\textbf{dynamic partitioning}(全局共用一个缓存池，动态分配缓存，按需分配)两种管理cache的方法。
